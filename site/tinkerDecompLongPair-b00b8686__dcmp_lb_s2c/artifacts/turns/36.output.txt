rc=0

57:| `min_reward` | number | 1.0 | `objective: sft` only: rows with `reward` >= this are trained on, the others dropped (a filter, never a weight) |

64-## Training data (`data`)
65-`data` names a JSONL file in your workspace (a path relative to the workspace, or absolute inside it): one line per training
66-prompt, `{"task": ..., "seed": ..., "variant": ..., "prompt": ...}` (`variant` and `prompt` optional, no other keys):
67-- `task`: a trainable task. `variant`: another trainable task of the same simulator task (e.g. `stack` with variant `revstack`; revstack runs under a scene shift and practises alone, so a dataset with revstack rows has no rows of any other task); the row then
68-  trains on `variant`. Any mixture of tasks and variants is allowed.
69-- `seed`: an integer >= 810001 (seeds 1-100 are the final score's, 800001-809999 are eval.py's dev seeds); all `rollouts`
70-  rollouts of the row run on that seed.
71-- `prompt`: replaces the task's user message for that row only (the system message stays). A row without `prompt` trains on
72-  the task's eval prompt, checked byte for byte before training; a row with `prompt` is not checked and counts as a prompt
73-  override, a method choice recorded with the adapter (`data.prompt_overrides` and `data.label` in training.json).
74-- Rows train in file order, `batch` rows per step: the row count must be a multiple of `batch`, and the call runs
75-  rows / batch steps (omit `steps`, or give that number). The call's tasks come from the rows (omit `task`); `note` and
76-  `goal` are not accepted with `data`. At most 4096 rows, 16 MB, 65536 characters per `prompt`.
77-- The file is copied when the call starts; training.json's `resolved_spec.data` and the train's result (`config.data`) record
78-  its `sha256`, `rows`, rows per task (`tasks`) and `prompt_overrides`.
79-
80:## SFT (`objective: sft`)
81:A spec `{"objective": "sft", "data": "<file>.jsonl"}` (optional: `name`, `init`, `epochs` (1), `batch` (16 rows per step), `lr`
82-(1e-4), `min_reward` (1.0), `time`; no other field) trains the policy's LoRA by supervised fine-tuning (cross-entropy on the program's
83-tokens only; LoRA rank 32 / alpha 64 on the policy's modules, or `init` continued; without `init` it continues the policy's own init,
84-as a practice call does). It runs on the small policy profiles (SCOREBOARD.md's `policy:` line names one, e.g. Qwen3-8B).
85-Availability is per policy profile: the session's turn-0 facts state it (`train objectives for this session's policy (...)`).
86-- Each line of `data` is `{"task": ..., "seed": ..., "prompt": [{"role": "system" | "user", "content": ...}, ...], "program": ..., "reward": ...}`
87-  (exactly these keys): `task` a trainable task (a hidden task by the name you see), `prompt` the chat the program answers (the user
88-  message last; `tasks/<task>/eval_prompt.txt` as messages is the eval prompt of record), `program` the response trained on, `reward`
89-  a number used only as the `min_reward` filter.
90-- `seed` is the scene the program ran on: seeds 1-100 (the final score's) and 800001-809999 (eval.py's dev seeds) are refused, so
91-  no reading you or the final score take is on a scene the policy was fitted on.
92-- A kept row whose prompt is not the task's eval prompt of record is a prompt override (a method choice): counted in
93-  `data.prompt_overrides` and labelled, as `note`/`goal` are.
94-- Steps = ceil(kept rows x epochs / batch); rows train in a fixed shuffled order; a row longer than 4096 tokens is dropped (`call.json`
95:  `sft_facts.dropped_too_long`). At most 20000 rows, 256 MB, 65536 characters per message or program.
96:- Building the file: `python3 skills/trainer/sft_rows.py practice adapters/<name> [--min-reward 1] [--steps 3-5] > sft.jsonl` takes a
97:  finished practice call's rollouts (Output below); `python3 skills/trainer/sft_rows.py rollouts rollouts/<id>.jsonl [--min-reward 1] > sft.jsonl`
98-  takes rollout.py rows (reward = your self_reward). Both print why each dropped row was dropped.
99:- Output: `adapters/<name>/` with the adapter, `sft_log.json` (per step: `step`, `loss`, `grad_norm`, `tokens`), `call.json` and
100-  `training.json` (`resolved_spec.data`: `sha256` of your file, `rows`, `kept`, rows per task, `min_reward`, `prompt_overrides`); the
101-  train's result shows the same under `config.data`. A cancel or a cluster stop keeps nothing (the adapter is saved at the end).
102-- Cost: 1 GPU x (0.05 + 0.000695 x steps x batch) canonical GPU-hours (the admission estimate counts every row of the file).

104-## Early stop (`stop_when`)
105-Optional. `{"plateau_steps": K, "min_gain": g}` stops the call once K steps in a row pass without the smoothed reward rising more
106-than g above its best so far; `{"reward_at_least": r}` stops it once the smoothed reward reaches r; with both, the first that
107-holds stops it. The smoothed reward is the mean `score_mean` of the last 3 steps, so neither can stop a call before step 3
108-(a call of fewer than 3 steps, or with 3 + K > `steps`, is refused). It is checked after every step. The adapter is the step it
109-held at (`stop_step`); the call is charged the steps it completed (`steps_run`, which can include a step that finished before the
110-stop took effect), and `training.json` / `call.json` record `stopped_early: true`, `stop_step`, `stop_reason` (`plateau` or
111-`target_reward`) and `steps_run`; the call's `state` is `STOPPED` (a finished call, not a failure). Without it, all `steps` run.
112-
113-## Defaults (identity-v2)
114-A spec with no fields (`{}`) continues your lineage on the whole task set with fresh seeds for the rest of your budget. A field you omit takes its default: `task` = this session's tasks (tasks.json) in one call, an equal split per batch; tasks with no practice unit here, and, in a set of several, tasks that practise alone (revstack; hidden tasks), are left out and listed with the reason; `batch` of a task list = the smallest number >= 8 that splits as asked; `steps` = as many steps as your remaining GPU-hour budget affords at this call's cost (budget minus GPU-hours charged minus the estimates of your running calls), at most what the Tinker spend cap affords when trainer=tinker; with no session budget, 1; not one step affordable: the call is refused, naming `steps` and the GPU-hours remaining (`data` and `init_mode: resume` set the steps themselves); `init` = the adapter this session trained last (none yet: a fresh LoRA); seeds = the lineage's next unused block. Every field can be set to override its default. Each `call.json`, `training.json` and job result carries `train_defaults`: `defaults` (`identity-v2`), `defaulted` (the fields that took their default), when `task` did, `task_set` (`source`, `tasks`, `left_out`), and when `steps` did, `steps_default` (`available`, `per_step`, `fixed`, `cap`, `steps`).
115-- resume: `init_mode: resume` + `init` (same lineage, the parent's full state)
116-- branch: `init_mode: branch` + `init` (a new lineage from the parent's weights)
117-- fresh: `init_mode: fresh` (a new LoRA, a new lineage)
118-
119-## Continuation
120-What a train starts from is one rule across sites (`init`, `init_mode`): without either, the adapter this session trained last is
121-continued (its lineage goes on); nothing trained yet means a fresh LoRA. `init` alone is the site's native continuation (stated in
122-its row). `init_mode` makes it exact: `resume`, `branch`, `fresh`. Every `call.json` / `training.json` records `continuation`
123-(`kind`, `parent`, `state_restored`, `parent_checkpoint_id`, `resume_from_step`), `lineage_id` (minted when a lineage starts, kept by
124-resume / continue, new on branch / fresh) and `checkpoint_id` (the weights' digest); the job result's `receipt.lineage` repeats
125-them. A `resume` whose parent's full state is gone is refused with that fact (start from its weights with `branch` instead). No
126-default picks an adapter by score: "last trained" is the one you trained most recently.

128-## Failures
129-A request this site cannot run as written ends `failed` in `jobs/<id>.json` with this text; nothing is charged:
--
139:- sft: `train: data line <N>: <rule>` (a row's keys, task, seed reserved, prompt, program or reward), `train: no row has reward >= min_reward <m> ...`, `train: field(s) [...] have no meaning with objective 'sft'; ...`, `train: objective 'sft' needs data: ...`, `train: objective 'sft' trains the small policy profiles on this site ...`, `train: steps <s> != ceil(kept rows x epochs / batch) = <n>; omit steps`, `train: task: an sft spec trains the tasks of its kept rows (...); omit task`
140-- `train: data line <N>: <rule>` for a row that breaks a rule above (not a JSON object; unsupported key(s); task must be one of ...; seed must be an integer; seed <s> is reserved ...; variant of '<task>' must be one of ...; prompt must be a non-empty string; prompt has <n> characters), or `train: data file has no rows` / `data has more than 4096 rows` / `data file is <n> bytes; at most 16777216`
141-- `train: data has <rows> rows, not a multiple of batch <batch>: ...` / `train: steps <s> != data rows / batch = ...; omit steps` / `train: task: a spec with data trains the tasks its rows name (...); omit task` / `train: note cannot be set with data; ...`
142-- `train: data file <path> is outside your workspace; a data file must be a file in your workspace` (a symlink is not followed either)
143-- `train: batch <b> does not split equally across <n> tasks [...]; use a multiple of <n>` / `train: task: each task at most once, got [...]` / `train: note edit one task's training prompt; a spec naming several tasks cannot set them` (a `task` list)
144-- `train: task 'revstack' runs its simulator under a scene shift and practises alone; name it in a spec of its own`
145-- `train: your reward function raised <Error>: <message> (reward.py line N); ...` / `train: your reward function tried to <action> (<detail>), which the reward sandbox refuses; ...` / `train: your reward function ran longer than 120 s on one rollout ...`: a custom `reward(r)` runs in a sandbox, once per rollout: plain Python and the interpreter's libraries (math, json, numpy), files only in its working directory (temporary), no other files, no network, no subprocesses, 60 s CPU and 4 GiB per call. The train stops at the first such failure.
146-- `train: seeds 1-100 are reserved for the final score; use dev seeds >= 800001`
147-- `train: stop_when...` for a `stop_when` that breaks a rule of Early stop above (the message names the rule)
148-- B2: `train: start_preset '<p>' is a registry preset, built with the privileged oracle; on a hidden task build your own start states with preset.py ...` / `train: start_preset '<p>' was built on task another task, not <task>`
149-A failure inside the trainer or the simulator (crash, missing adapter files, a hidden seed used) ends the session as an infrastructure
150-fault. An all-zero update is a training outcome, shown on the scoreboard: the adapter's change is zero, so it behaves as its init (base or the init adapter).

152-## Progress and cancel
153-While a train runs, its record shows completed steps, the latest step's mean reward, the fraction of rollouts with reward > 0
154-and canonical GPU-hours of the steps done so far (read from the trainer's per-step output about once a minute). A checkpoint is saved every
155-step. A call stopped by the cluster (time limit, preemption, node failure) continues from its last checkpoint in a new Slurm job, at most 3 times; its status then says `continued from step k in job J`, and its result lists every Slurm job (`jobs`) and each continuation (`continued`: `job` stopped, `cause`, `from` step, `of` steps, `continued_in` job), as it lists site retries.
156-`cancel.py ID` stops the job and keeps the adapter of the last saved step (registered with the steps it ran), or ends the
157-job `failed` if none was saved; either way the job is charged the canonical cost of the steps it completed (see Cost).

180-## Output
181-A finished train writes `adapters/<name>/` (read-only to you): `adapter_model.safetensors`, `adapter_config.json`,
182-`rewards.json` (per step: `step`, `score_mean` over that step's rollouts), `call.json` (job ids, `gpu_hours` = the canonical charge to
183-your budget, `gpu_hours_actual` = measured hardware time, not charged, nonzero LoRA-B count, rollout seed range) and `training.json` (`resolved_spec`: the controls actually used). The adapter can then be named in `eval.py --adapter`, `load.py`, or as `init` of another train.
184-Each `rewards.json` step also has `zero_variance_frac` (the share of that step's prompt groups whose rollouts all got one reward) and `failure_stages` (failed rollouts by stage: `sim`, `timeout`, `program`, `grader`, `task`); the running job's status line shows them for the latest step and the train's result lists them per step (`step_facts`).
185-A call of several tasks (a `task` list, or `data` naming several) adds `per_task` to each `rewards.json` step: `{task: {"score_mean", "rollouts"}}`, that step's rollouts of each task and their mean reward (a rollout is attributed by its prompt; one matching no single task is left out).
186:Each finished train (and one kept at a stop) also writes `practice_rows.jsonl`: one line per rollout of the call, `{task, seed, prompt_sha, program, reward, step, start}` plus the episode's `stdout_tail`, `sandbox_rc`, `secs`, `task_completed`, `sim_reward` (the reply's `reward`), `stages`, `final_state` and `trace` (reward = the score GRPO gave it; start = the adapter the call started from), with the prompts in `practice_prompts.json` (`{prompt_sha: [chat messages]}`). A rollout whose program was written for two seeds in one step is left out. These are training data you generated yourself; `skills/trainer/sft_rows.py practice adapters/<name>` turns them into SFT rows (see SFT below).
187-Each such train also writes `train_data_digest.md` (and the same as `train_data_digest.json`) next to `practice_rows.jsonl`, over its rows: rollouts, unique programs, nonzero-reward share, GRPO groups (the rollouts of one prompt) with the all-zero and zero-variance ones; the same per step and, for a call of several tasks, per task; and the 3 highest- and 3 lowest-reward rollouts with task, step, seed, reward, program and their line in `practice_rows.jsonl`. The train's job result carries `train_data`: the digest's path and those counts.

189-The job result of a finished train also carries `receipt` (site facts): `curve` (per step: `score_mean`, `zero_variance_frac`, `rollouts_per_step`, and `per_task` curves for a multi-task call), `slopes` (mean change of `score_mean` per step over the last 3 steps and over the whole call; numbers over those windows, nothing more), `stop` (`state`, `reason` = the stop rule's reason, a cluster stop, or `max_steps`; `steps_run`, `steps_declared`, `adapter_step`), `lineage` (`parent` = `init`), `seeds` (the range and count the rollouts used), and `evals` (how many dev evals this adapter and its parent already have in this session; `marker: "not evaluated"` when it has none).
