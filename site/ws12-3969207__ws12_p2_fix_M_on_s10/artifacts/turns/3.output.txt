## decomposition — what a practice sub-goal did and did not do (2026-10-29, #10; staged-reward + start-preset + stage-wise curriculum arc)

On the zero-signal tasks (nut, restack) the binary task-completion reward is all-zero across a GRPO group, so there is no gradient. A sub-goal practice reward + a start-state preset can supply one. What the runs showed (DEV / Qwen3.8-27B; all paths under `$R/pskills/rl/capx_rl/runs/`):

**A REACHABLE sub-goal unlocks the tail.** restack trained FROM a lifted start preset (red grasped+lifted; train align->place) under a staged reward on the tail: binary completions 3/64 -> 8/64, nonzero 13 -> 20/64 over 25 GRPO steps (`train_13962063`). The align->place tail is reachable from lifted, so the policy learns it.

**A sub-goal BEYOND the policy does nothing, and aiming at one wastes capacity.** nut trained FROM a grasped start preset (train align->insert) was completely FLAT — binary 0, nonzero 0, mean 0.0 across all 25 steps (`train_13962061`): nut-align is beyond the 27B policy even from the closest (grasped) start. A nut adapter aimed at align also caused FORGETTING (net-negative: dev lift 77->66, stack 54->51, no gain). Lesson: a staged reward needs a REACHABLE sub-goal; aiming beyond the policy wastes capacity and forgets.

**The preset gain does NOT transfer to from-scratch for free.** Continuing from the preset-trained adapter but training FROM SCRATCH (full chain, no preset) gave 0 from-scratch binary on both: restack hill-climbs to the single easiest sub-goal (unstack, depth-1 54/64) and the within-group variance COLLAPSES 0.015 -> 0.006 -> no gradient past the first barrier (`train_13974952`); nut climbs to reach+grasp (staged 0.027 -> 0.301) but never align/insert (`train_13974953`). Standard dev eval confirms: base restack s4v2 0/100 -> from-scratch adapter 0/100; base nut 0/100 -> 1/100 (noise). The tail-knowing init does not help because the tail state is never reached from scratch.

**Keeping variance alive across a depth MIXTURE is the lever.** A mixed start-state pool (per-GRPO-group mixture of lifted/grasped/scratch, full-chain staged reward so scores SPREAD across depths) keeps within-group variance ALIVE where from-scratch collapsed: restack phase A held var ~0.08 (vs 0.006), staged_mean climbed 0.23 -> 0.35, and the grasped start went from 96% -> 54% program-failure (the curriculum taught it, reaching depth 3-4). Scratch-start was still at the unstack barrier (0 from-scratch binary) as of phase A; the shift-toward-scratch schedule (phases B/C) is in progress (`train_13989823`; mixes under `$R/artifacts/start_presets/mixes/`).

**THE KEY TEST-TIME (B2) LESSON: shaping on the privileged reward is NOT a subtask.** Everything above used the DEV-mode privileged path (the simulator's privileged staged reward + registry presets). That path proves the mechanism but is not a capability the model keeps at test time. In hyak records only 22/344 practice calls defined a reward.py, and every sampled one was "task_completed else a small weight on the simulator's STAGED (privileged) reward" = shaping on the privileged signal, never a new sub-goal CHECK; 0/344 used a start preset. The capability exists; the behaviour does not — no session has authored a real subtask with its own verifier. And nothing blocks it: `retrain_min/site/fairsc3_jobs.py` (the hidden-task guard) already FAILS CLOSED on a privileged reward (task_completed/shaped) for a hidden cell, so on hidden cells the ONLY allowed reward is the agent's own `reward.py` (over `log_tail`). The gap is purely authoring friction. A real subtask = the agent's own reward.py parsing the program's PRINTED observations from log_tail + its own start from its own (non-privileged) prefix program + a note naming the sub-goal. The evidence shows decomposition works WHEN the sub-goal is reachable and verified; the non-privileged authoring is what makes it a B2 capability rather than a dev-phase trick.

**Stage-wise mixture result (phases A->B->C complete, 2026-10-29): the barrier MOVES from stage 1 to the final stage, but the final precise manipulation stays the wall — on BOTH tasks.** Running the full shift-toward-scratch schedule (restack lifted/grasped/scratch -> grasped/scratch; nut grasped/reached/scratch -> reached/scratch; full-chain staged reward throughout) moved the from-scratch policy up the chain stage by stage. restack FROM SCRATCH went from the naive depth-1 unstack plateau (54/64, var collapsed 0.015->0.006) to reliably reaching ALIGN (phase C: depth-3 820/1280 = 64%, depth-4 16) — i.e. unstack->grasp->lift->align, 4 of 5 stages, from scratch — but the FINAL place (ON) never completes: 0 from-scratch binary in training AND `restack from-scratch DEV eval 0/100` (base 0/100). nut FROM SCRATCH reaches grasp reliably (phase C depth-2 1049/1281) and NICKED insert twice (2/1281 in-training = 0.16%, noise floor); `nut from-scratch DEV eval 1/100` (base 0/100). The restack(0)/nut(noise-floor) split is NOT "nut unlocks, restack doesn't" — both final precise stages sit right at the edge of crossable, and nut happened to nick it this run. MECHANISM for the residual wall: within-group variance COLLAPSES at the deepest reliably-reached stage (restack phase C var 0.059->0.02 as scores cluster at align=0.6), so the gradient to push the LAST stage weakens exactly where it is needed; and the final phase dropped the deepest preset (lifted/grasped) so the clean-start final-stage skill (the single-preset restack-from-lifted that gave binary 8/64) is no longer reinforced. So: decomposition via a depth-mixture curriculum UNLOCKS the chain up to the last precise manipulation stage from scratch, but the final precise place/insert is the residual barrier.

**Transfer (8-task forgetting, phase-C adapters, DEV):** the restack chain-practice adapter is a BETTER GENERALIST, not a forgetter — wipe 20->49 (+29), stack 54->61 (+7), twolift/handover 1->3, nut 0->0, only lift 77->64 (-13). (Contrast the single-preset nut-align adapter, which was net-negative.) nut phase-C transfer: lift 77->61 (-16), stack 54->59 (+5), wipe 20->29 (+9), restack 0->0 (flat), twolift/handover 1->0 (noise). A weaker generalist than the restack adapter, consistent with nut getting less far up its chain. So chain-practice that unlocks most of a zero-signal task's chain can produce broadly transferable manipulation skill even without the task's own binary.

## A. Subtask with your own verifier + start state (the B2 decomposition recipe)

- **A1 (reframes v16 item 1).** Shaping the simulator's privileged/staged reward has not lifted a base-0 task in the
  recorded runs (EVIDENCE #shaped-0pct, #hyak-trace); of the practice calls that defined a `reward.py`, most shaped that
  privileged signal and none authored a new sub-goal CHECK or used a start preset (EVIDENCE #decomposition). A real
  subtask is largely untested. Try one small call: your own `reward.py` scoring a sub-goal from the program's PRINTED
  observations (`log_tail`), started from your own prefix program, and count `task_completed` on a few seeds before
  scaling.
- **A2.** On hidden cells the privileged reward modes (`task_completed`, `shaped`) are refused and only `reward(result)`
  over `log_tail` is accepted (tools: B2 appendix; `fairsc3_jobs.py` fails closed). `log_tail` is the only observation
  your reward sees, so a silent program scores nothing. Try making programs PRINT the `get_observation()` values and the
  object/gripper poses your sub-goal depends on (before/after each move); check the spread with `rollout.py --reward FILE`
  before you train.
- **A3.** A sub-goal lifted the tail only when it was REACHABLE from the chosen start (EVIDENCE #decomposition: restack
  trained from a lifted preset raised completions; an unreachable aim did not). Before training a sub-goal, roll out a
  handful from your start program and confirm some rollouts reach the sub-goal state at all; if none do, pick a closer
  start or an easier sub-goal.
- **A4.** A sub-goal BEYOND the policy stayed flat (0 completions, 0 nonzero reward) and the adapter went net-negative on
  other tasks (forgetting) (EVIDENCE #decomposition). If a few steps show an all-zero group, treat it as beyond-reach and
  re-pick rather than training longer; re-measure the earlier skills to catch forgetting.
- **A5.** The `decompose` helper names the failing step correctly, but the practice tasks that actually LEARN are the ones
  with a nonzero base rate (tools: decompose SKILL.md / E11). Try the helper for ideas (free, one LLM call, ~10/session);
  prefer the decomposed sub-goal that already shows a few completions from your start.
- **A6.** `reward_check` drops a reward that pays on an untouched or knocked-over scene, or never pays on a checked expert
  success (tools). Try running `reward_check` on your `reward.py` before you pay for training; a reward that scores every
  rollout the same gives GRPO nothing to learn from.

## B. Curricula / training-order

- **B1.** The biggest single-task gain came from the highest-HEADROOM task (low base, but real signal), not from pushing
  already-strong tasks (EVIDENCE #pin3-trace, #fair-sc-3-trace item 10). Try ranking the set by headroom x "base shows
  some completions" and committing early to the top one; check base completions cheaply first.
- **B2.** Stacking skills in sequence: a long 2nd-skill train eroded the 1st (EVIDENCE #pin3-trace g08). Try keeping each
  later train SHORT and re-measuring the earlier skill afterward; cancelling keeps the last saved step.
- **B3.** Training one task shifts others up or down, and one adapter can carry a tax on a sibling (a stack adapter
  over-fit the red cube and taxed revstack; EVIDENCE #pin3-trace, #shaped-side-effects, #fair-sc-3-trace). Try measuring a
  candidate on the task it most likely taxes before committing it.
- **B4.** A mixed start-state / depth curriculum kept within-group variance alive where from-scratch collapsed (EVIDENCE
  #decomposition: a per-group mixture of lifted/grasped/scratch spread scores across depths and climbed). On a task that
  trains from a preset but gives 0 from-scratch, try a start-state MIXTURE and watch whether group variance stays nonzero.
- **B5.** The preset-trained gain did not transfer to from-scratch for free (EVIDENCE #decomposition): the policy
  hill-climbs to the easiest sub-goal and variance collapses past the first barrier. If you train from a preset, plan a
  schedule that shifts starts toward scratch and re-check from-scratch completions, rather than assuming the skill
  transfers to the eval's own start.

## C. Data / reward mixtures

- **C1.** Keeping a mixture of start depths per GRPO group kept a gradient alive where a single hard start gave none
  (EVIDENCE #decomposition). Try mixing start states within a group so some rollouts land in a scorable region; check that
  staged_mean climbs and variance does not collapse to ~0.
- **C2.** The reward shape matters: a full-chain staged reward (scores spread across depths) kept variance; a binary
  all-or-nothing reward on a 0-base task gave a flat all-zero group (EVIDENCE #decomposition, #shaped-0pct). On a sparse
  task, try a reward with graded intermediate credit over the printed observations so rollouts differ; check the per-step
  reward spread.
- **C3.** One adapter meant to help several tasks risks regressing the one you never evaluated (EVIDENCE #fair-sc-3-trace
  item 2: a global adapter regressed an eval-only task to 0). If one adapter will serve several tasks, try evaluating it on
  each of them, including eval-only / base-0 ones, before shipping.

## D. SFT / self-distillation on your own material

- **D1.** The trainer has a second objective, `sdft` (self-distillation of a text skill into the weights): it needs no
  reward and gives a signal even on a task with no successes (tools: train_grpo "Objectives"). On a base-0 task where GRPO
  has no gradient, try writing a short text skill describing the maneuver and `sdft`-ing it in, then measure whether
  completions appear. Untested here.
- **D2.** Objectives chain through `--init` (sdft then grpo, or grpo then sdft) (tools). Try `sdft` to seed a behaviour,
  then a short `grpo` train to sharpen it on the reward; compare against grpo-from-base on the same budget.
- **D3.** `sdft` runs its max steps (the reward-curve stop options do not apply) and records `kl_curve`, not a reward
  (tools). If you sdft, budget the fixed step count up front and read `kl_curve` (student-minus-teacher logprob) for
  convergence instead of expecting an early stop.
- Note: "SFT on your own filtered rollouts" from the literature maps, in this harness, to distilling a text skill (your
  own best written explanation) via `sdft`; there is no separate filtered-rollout SFT tool, so frame it as D1/D2.

## E. Chaining adapters (vs loading pairs)

- **E1.** Chaining (train B continuing from A's adapter via `--init <A>`) kept BOTH skills where a fresh-adapter PAIR
  dropped one (EVIDENCE #pin3-trace confound-free cell; #fair-sc-3-trace c09 chain topped the batch). To combine two
  skills, try a chain rather than two fresh adapters loaded together, and compare chain vs pair in one batch.
- **E2.** Pairs combined well AND badly, and collapse is adapter-specific (EVIDENCE #pair-collapse: 8B pairs collapsed
  under an init-adapter confound; one 27B dev pair held, another dropped a component). If you do load a pair, try
  evaluating each adapter ALONE and the pair in the same batch so a collapse is visible before you ship.
- **E3.** A long 2nd train on a chain eroded the 1st skill (EVIDENCE #pin3-trace g08). Keep chained trains short and
  re-measure the earlier skill; if it dropped, roll back a step (cancel keeps the last saved step).
- **E4.** `finish.py` can ship a DIFFERENT stack per task (tools: `--per-task TASK=STACK`). Rather than forcing one global
  adapter onto all tasks, try shipping each task its own best-checked stack (base for the rest); confirm the final
  per-task assignment on every task.

## F. Budget allocation across the set

- **F1.** Planning the budget up front, reserving checking evals and loads, let early commitment to signal-bearing tasks
  pay off (v16 item 9); a train is refused if the budget cannot pay (tools). Try writing the plan first: reserve rollouts
  for checks, allocate the rest to top-headroom tasks.
- **F2.** Sessions stopped with budget left that could have fit another train+checks (EVIDENCE #hyak-trace item 11 /
  header). Before ending, try checking whether a short second train on another signal-bearing task still fits; a second
  train has added to the first (v16 item 11).
- **F3.** Queues took hours; many short re-polls wasted attention versus one long wait (EVIDENCE #hyak-trace item 7).
  Submit the jobs you want together, then wait in long windows (waiting is not charged).
- **F4.** Reference scores from other sessions are not this session's targets (EVIDENCE header; #hyak-trace header: a
  session stopped citing another's hidden total). Spend against your own measured headroom, not a remembered number.

## G. When to stop a train

- **G1.** Gains flattened after a moderate number of steps; a run kept past its peak (reward falling) lost its gain and
  hurt other tasks (v16 item 5; EVIDENCE #hyak-trace item 5). Read the reward curve before extending; if it has fallen
  from its peak, cancel (keeps the last saved step) rather than run to max.
- **G2.** The trainer has curve-reading stop options `--patience / --delta / --target-success / --window` (tools). Try
  setting a target or patience up front so a plateaued train stops itself instead of spending to max steps.
- **G3.** On equal-reward rollouts (no within-group gradient), changing the start state or reward beat training longer
  (v16 item 3). If a group's rewards are all equal, try changing the start or the reward rather than adding steps.

## H. How to check regressions cheaply

- **H1.** `rollout.py --reward FILE` adds `self_reward` per seed and its mean, charged as an eval of N seeds (tools). Use
  it to measure a sub-goal or sanity-check a reward on a few seeds BEFORE training, and to spot-check a trained adapter on
  the task you fear it taxed.
- **H2.** Training-seed scores (`rewards.json`) and held-out dev evals have differed; prefer the held-out number (v16
  item 6). When a training curve looks good, confirm on held-out dev seeds before trusting it.
- **H3.** An eval that ended with NO count (timeout, no seed scored) says nothing about the adapter; a rerun cost less than
  dropping it (v16 item 12; EVIDENCE #hyak-trace item 12). If an eval returns no count, rerun a few seeds before
  discarding the adapter.
- **H4 (reframes v16 item 2).** The submitted adapter serves EVERY task, so it can regress one you never evaluated,
  including eval-only / base-0 (EVIDENCE #fair-sc-3-trace item 2). Before finishing, try a cheap check of the FINAL served
  stack on every task, not only the ones you trained.
- **H5.** Keep the best checked stack loaded as you go, so a cut-short session still ships one (v16 item 8).

## Reframed "Did not work" (v16's prohibition section -> try-and-check)

- **R1 (preset-start / cube-in-hand).** A practice start state the evaluation never reaches (e.g. the cube already in
  hand) gave almost no successful rollouts at eval, and preset gains did not transfer to from-scratch for free (EVIDENCE
  #decomposition; #v15-moved-numbers). If you train from a preset, remember eval starts from scratch: try a curriculum
  that shifts starts toward scratch and check from-scratch completions, rather than assuming the preset-trained skill
  shows up at eval.
- **R2 (training-only note).** A note added only to the training prompt did not carry to evaluation; it edits the prompt
  text, not the trained task (EVIDENCE #v15-moved-numbers: training rollouts completed but eval scored 0). If you want a
  behaviour at eval, try baking it into the weights (train / sdft) or into a sub-goal reward, and confirm on held-out dev.
