### Worked loop (a task T whose policy suffix fails at some cut)

```
python3 rollout.py --adapter loaded --task T --seeds 8 --magic-prefix stage=<k>                # policy suffix at cut k (cuts: below)
python3 rollout.py --adapter loaded --task T --seeds 8 --magic-prefix stage=<k> --suffix oracle  # doability, counts only
# c = the first cut whose policy suffix fails while the oracle passes; if the oracle fails too, report c, do not train
python3 rollout.py --adapter loaded --task T --seeds 8 --magic-prefix stage=<c> --magic-presets T_c   # saves T_c_pre / T_c_post
python3 verifier.py design --task T --goal "<T's goal in your words>" --purpose "reward after cut c" --name T_goal
python3 reward_check.py --reward verifiers/T_goal.py --against T_c                            # rises pre -> post? crashes lowest?
python3 unit.py register T_after_c --task T --reward verifiers/T_goal.py --start-preset T_c_post
python3 rollout.py --adapter loaded --task T_after_c --seeds 8                                 # signal = some rows pay, not all
echo '{"name": "A_c", "task": "T_after_c"}' > spec_c.json && python3 train.py spec_c.json       # reward check runs before any spend
python3 eval.py --adapter A_c --task T_after_c --seeds 8                                       # the unit's own scoreboard row
python3 rollout.py --adapter A_c --task T --seeds 8 --magic-prefix stage=<c-1>                 # chain back: the cut before c
# once A_c passes from cut c-1, repeat from the --magic-presets step at c-1 with "init": "A_c" in the spec
python3 eval.py --adapter A_c --task T --seeds 20                                              # the task's own count
```
A verifier reads `final_state`: use it with rollout.py, unit.py and train specs; eval.py rows carry no `final_state`.

Magic ladder cuts of your tasks (`--magic-prefix stage=<k>` or `stage=<name>`):
- nut: 0=grasp, 1=lift, 2=align, 3=lower
- restack: 0=grasp, 1=lift, 2=align, 3=lower
- revstack: 0=grasp, 1=lift, 2=align, 3=lower

## Verifiers (this session)

| Command | Effect |
| --- | --- |
| `python3 verifier.py design --task T --goal TEXT [--unit U] [--purpose TEXT] [--name N]` | A verifier for your goal (or sub-goal) on T, written and reviewed by fresh-context subagents and executed by a lint on states: T's start state scores 0, crashed and no-op rows score 0, goal states score 1, near misses (states that look like the goal but are not: the task's fixed set and the judge's) score 0, and the mean score never falls along T's stage checklist. Writes `verifiers/N.py` (a reward for rollout.py --reward, unit.py and a train spec; eval.py rows carry no `final_state`, so it scores 0 there) and `verifiers/N.audit.json`, or refuses naming the failing check. Uses only your own recorded rows of T: run rollout.py on T first. The subagents' time is charged to your GPU-hour budget (`gpu_hours` in the result). Example: `python3 verifier.py design --task T --goal "sub-goal 1 reached and released" --purpose "reward of sub-goal 1"` |

- A reward you write over stages/task_completed needs no verifier; verifier.py design is for a goal the stage checklist does
  not name, and is the only path that runs a check against near misses before you train on it.
- The default reward is a binary current-sub-goal verifier: 1.0 when the sub-goal's predicates hold on `final_state`, else 0.0,
  with no distance term.
- Relax only within bounds: a larger tolerance on the same predicate, or an earlier sub-goal. Never drop a necessary predicate;
  never relax the task's final success.
- Tighten or move on once a sub-goal passes above ~60%.
- Before submitting a verifier or reward, write down one end state that passes your predicates without achieving the goal; if
  you can write one, the predicate set is incomplete.
- A verifier is a reward, never a score: the eval of record stays the task's own check.

# Trainer on this site (hyak, CaP-X Robosuite, GRPO LoRA)

`python3 train.py SPEC` submits one practice call; SPEC is a JSON or YAML file in the workspace. `python3 train.py --help` prints this file.
Relative paths in SPEC (a reward file, an init adapter path, data files) resolve against the workspace, where `train.py` runs, wherever SPEC itself is.
The programs can call exactly the functions listed under `APIs:` in the task's eval_prompt.txt. The Key rules of the stack,
revstack, stackv2 and handover prompts also name `get_object_pose`, `sample_grasp_pose`, `goto_pose_arm*` and a `z_approach`
parameter: none of these exists in these cells (the rules text is shared with the tasks' privileged-API variant). The prompts
are the benchmark's cells of record and are scored as they are.
A stack (`eval.py --adapter A,B`, `load.py stack`) holds at most 2 adapters: each is rank 32 and the serving's maximum
LoRA rank is 64; a larger stack ends `failed` with `stack rank 96 > 64 (the serving's --max-lora-rank): at most 2 adapters of rank 32`.

## What a practice call is
GRPO on LoRA adapters of the policy model named in SCOREBOARD.md's `policy:` line (LoRA rank 32, alpha 64, on q,k,v,o,out,gate,up,down
projections for Qwen3.8-27B; other policies have no `out`).
Each step: `batch` prompts x `rollouts` rollouts (8, or 16 if the spec sets it). GRPO's update comes from reward differences among a prompt's rollouts: a prompt whose rollouts all get the same reward adds nothing to it. A rollout is one program written by the model for the task, run once in the task's simulator
on one seed; its score is the reward below. The training prompt is the task's evaluation prompt, byte for byte (checked before training), unless the spec sets `note` or `goal` or a `data` row sets `prompt`:
those are part of the training prompt only. Every eval, including the final hidden-seed score, uses the task's
`tasks/<task>/eval_prompt.txt` in the workspace verbatim, without any note or goal.
Sampling during practice: temperature 1.0, top_p 0.95, top_k 20; at most 8192 generated tokens per program.
Sampling during evaluation (eval.py and the final score): temperature 0.7, top_p 0.8, top_k 20, presence_penalty 1.5, thinking
off; at most 8192 generated tokens per program (envs/capx/config_of_record_v4.yaml). For lift, stack, wipe and nut the practice
unit and the eval cell run the same task config (`*_reduced_api_exampleless.yaml` is the s4:paper cell's config).

A policy whose name carries `+init:<sha>` (SCOREBOARD.md's `policy:` line) is the model plus that init adapter: its base is
served with the init, every train without `init` starts from it, so each trained adapter already contains the init's change,
and a stack of two such adapters applies that change twice.
