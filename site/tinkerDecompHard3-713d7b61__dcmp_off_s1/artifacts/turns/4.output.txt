# Environment tools
Read `ENVIRONMENT.json` for the site's policy, adapter composition and enforced constraints, and `tasks.json`
for task details. `STATUS.json` contains the latest budget, loaded stack, adapters and running job IDs.
`SCOREBOARD.md` has dev scores and lineage. While a train or eval is submitted, `jobs/<id>.json` (`progress`, `progress_line`; `status.py`),
STATUS.json (`job_progress`) and the scoreboard show whether it is queued (not started, with its queue time so far) or running, and for a
running train its completed steps, latest mean reward and GPU-hours so far, as the site reports them. `tasks/<task>/eval_prompt.txt` (when
the site provides it) is the prompt the policy receives at evaluation; training prompts are checked against it. `tasks/INDEX.md` lists each task's goal line, dev and
hidden seed ranges, recorded base score, API names and key rules, taken from tasks.json, the eval prompts and the base scores. State comes from the environment; this skill is editable guidance.
| Command | Effect |
| --- | --- |
| `python3 train.py SPEC` | Submit JSON/YAML spec to the installed trainer; see `skills/trainer/SKILL.md`. |
| `python3 eval.py --adapter A[,B...]\|base\|loaded --task T --seeds N` | Evaluate on the next N unused dev seeds (the result lists them; the base column has its own) with the task's `tasks/<task>/eval_prompt.txt` verbatim (no training `note`/`goal`; the final score uses the same prompt). A stack's score on a task is known only from an eval of that stack (`--adapter A,B`); neither the scoreboard nor the environment derives it from its adapters' single scores. `loaded` is the stack loaded when the request is picked up, so not an adapter whose train is still running. Results are written only when all seeds finish, so an eval that reaches its time limit usually fails with no count (rarely: a count over the seeds that finished, with `partial`). Where the site can resume an eval (eval port dq-t1v2), an eval stopped by the cluster (time limit, preemption, node failure) continues its remaining seeds in a new Slurm job, at most 3 times; its status then says `continued from seed k in job J`, and its result lists every Slurm job (`jobs`) and each continuation (`continued`: `job` stopped, `cause`, `from` seed, `of` seeds, `continued_in` job), as it lists site retries. |
| `python3 load.py load A [B...]` | Replace the loaded stack (names separated by spaces; eval.py separates them by commas). |
| `python3 load.py stack A [B...]` | Append to the loaded stack. |
| `python3 load.py unload [A...]` | Remove names, or return to base with no names. |
| `python3 status.py [ID...]` | Read job states and results; no IDs shows all jobs. The last line states what finishing now would score. |
| `python3 wait.py all\|ID... [--max 4h\|90m]` | Submit a wait barrier: your next turn starts when those jobs finish or after `--max` (default 2h), whichever comes first. If the bound comes first, the result states each job's queue state, reason, position and time pending, and "no job finished". The barrier runs in the environment after your command returns, so `--max` is not limited by the per-command time limit. |
| `python3 finish.py [--policy base \| --adapters A[,B...]] [--note TEXT]` | Step one of ending the session: submit the policy to score (no policy arguments: the loaded stack; single mode: `current`, `v<k>` or `current@<k>`). The result states exactly what will be scored and a token. |
| `python3 finish.py --confirm TOKEN` | Step two, in a later turn: end the session; the submission is scored. |
| `python3 cancel.py ID` | Stop a running train or eval. A train keeps the adapter of its last saved step (if the site saved one), registered with the steps it ran; the job is charged the GPU time it used. |
Scripts submit request files and return IDs. Shell success means submission, not job success. In the chat backend,
requests are handled only after the entire command returns: `train.py spec.json; wait.py all; load.py load a1`
queues a dependency chain, but reading status later in that same shell still sees the old state. The Codex backend has a background executor; request processing and status refresh happen independently.
Read `jobs/<id>.json` or the next observation to distinguish done, failed and refused requests.
Training names are reserved while pending. Training does not load an adapter in library mode; single mode automatically
replaces and loads `current`. When ENVIRONMENT.json `constraint` names versions, every successful train is a new version
v1, v2, ... (`current` = the latest) and becomes active; `load.py load v<k>` makes an earlier version active again,
`eval.py --adapter v<k>` evaluates one, the next train starts from the active version, and versions are never stacked.
Adapter composition depends on the site. Load calls are free. Train/dev calls reserve the
site's cost estimate at admission and are charged the site's cost per call (skills/trainer/SKILL.md, Cost); the
reservation is admission control, not a hard runtime cutoff.
Successful training returns an adapter path, a skills digest, and site-provided training metadata when available.
`training.json` in the adapter contains site-resolved parameters and artifact names. `site_sources` identifies the site
code, not the complete external GPU/software environment. A skill edit alone does not change the installed trainer.
Ending the session takes two steps: `finish.py` submits a policy and its result states exactly what will be scored
(adapters with version and weights sha, eval-prompt hash) and a token; `finish.py --confirm TOKEN` in a later turn ends the
session. Until then the session goes on; a `load.py` or `train.py` request in between cancels the submission (submit
again). An unknown adapter name refuses the submission. The submission is scored even if a different stack is loaded at
the end. If the session ends without a confirmation (budget, caps), the pending submission is scored, else the loaded
stack. Submitted jobs finish before the score. A file named `DONE` starts the two-step finish like `finish.py` with no
arguments: it submits the loaded stack (the file is removed); the session ends only after `finish.py --confirm TOKEN`.

# Trainer on this site (hyak, CaP-X Robosuite, GRPO LoRA)
`python3 train.py SPEC` submits one practice call; SPEC is a JSON or YAML file in the workspace. `python3 train.py --help` prints this file.
Relative paths in SPEC (a reward file, an init adapter path, data files) resolve against the workspace, where `train.py` runs, wherever SPEC itself is.
The programs can call exactly the functions listed under `APIs:` in the task's eval_prompt.txt. The Key rules of the stack,
revstack, stackv2 and handover prompts also name `get_object_pose`, `sample_grasp_pose`, `goto_pose_arm*` and a `z_approach`
parameter: none of these exists in these cells (the rules text is shared with the tasks' privileged-API variant). The prompts
are the benchmark's cells of record and are scored as they are.
A stack (`eval.py --adapter A,B`, `load.py stack`) holds at most 2 adapters: each is rank 32 and the serving's maximum
LoRA rank is 64; a larger stack ends `failed` with `stack rank 96 > 64 (the serving's --max-lora-rank): at most 2 adapters of rank 32`.
Your shell on this site writes only in the workspace and has no network (pip, curl and similar fail) and no Slurm client;
all compute goes through train.py and eval.py.
## What a practice call is
GRPO on LoRA adapters of the policy model named in SCOREBOARD.md's `policy:` line (LoRA rank 32, alpha 64, on q,k,v,o,out,gate,up,down
projections for Qwen3.8-27B; other policies have no `out`).
Each step: `batch` prompts x `rollouts` rollouts (8, or 16 if the spec sets it). GRPO's update comes from reward differences among a prompt's rollouts: a prompt whose rollouts all get the same reward adds nothing to it. A rollout is one program written by the model for the task, run once in the task's simulator
on one seed; its score is the reward below. The training prompt is the task's evaluation prompt, byte for byte (checked before training), unless the spec sets `note` or `goal` or a `data` row sets `prompt`:
those are part of the training prompt only. Every eval, including the final hidden-seed score, uses the task's
`tasks/<task>/eval_prompt.txt` in the workspace verbatim, without any note or goal.
Sampling during practice: temperature 1.0, top_p 0.95, top_k 20; at most 8192 generated tokens per program.
Sampling during evaluation (eval.py and the final score): temperature 0.7, top_p 0.8, top_k 20, presence_penalty 1.5, thinking
off; at most 8192 generated tokens per program (envs/capx/config_of_record_v4.yaml). For lift, stack, wipe and nut the practice
unit and the eval cell run the same task config (`*_reduced_api_exampleless.yaml` is the s4:paper cell's config).
A policy whose name carries `+init:<sha>` (SCOREBOARD.md's `policy:` line) is the model plus that init adapter: its base is
served with the init, every train without `init` starts from it, so each trained adapter already contains the init's change,
and a stack of two such adapters applies that change twice.
## Spec fields (a spec with any other field fails; see Failures)
| field | type | default | accepted |
|---|---|---|---|
| `task` | string or list | this session's task set (see Defaults) | a trainable task (see workspace/tasks/INDEX.md), or a list of them: one call practising all, every batch split equally across them or by `weights` (no `note` / `goal`); revstack practises alone |
| `name` | string | `a<job id>` | letters, digits, `_ . -`, at most 48; not already taken, not `base` / `loaded`. Single-adapter mode: omit it (or `current`) |
| `steps` | integer | as many as your remaining budget affords (see Defaults) | any positive integer (cost grows with it, see below) |
| `batch` | integer | 8 (a task list: the smallest batch >= 8 that splits as asked) | prompts per step (each x `rollouts` rollouts) |
| `weights` | list of numbers | none: an equal split | with a `task` list: one weight per task, same order, each > 0; task i gets batch x w_i / sum(weights) prompts in every batch, which must be whole numbers (equal weights = the equal split); not with `data` |
| `rollouts` | integer | 8 | 8 or 16: rollouts per prompt (each prompt's GRPO group; `zero_variance_frac` under Output is the share of groups that added nothing). 16 doubles each step's rollouts and the per-step part of its cost |
| `lr` | float | 2e-5 | learning rate |
| `init` | string | none: the adapter this session trained last is continued natively (none yet: a fresh LoRA); see Continuation | an adapter name produced by an earlier train of this session (`base` is not one). Alone it means the site's native continuation: verl starts from its weights with a fresh optimizer; trainer=tinker restores its full state. Single-adapter mode: omit it (or `current`) |
| `init_mode` | string | none (see `init`) | what the call starts from, exactly: `resume` (same lineage; the parent's full state, weights + optimizer + dataloader, so `steps` is the target total and must exceed the parent's step), `branch` (a new lineage from the parent's weights, fresh optimizer; parent recorded), `fresh` (a new LoRA; no `init`). `resume` / `branch` need `init` |
| `start_preset` | string | none | a named start-state preset (core/start_presets.py: `restack_grasped`/`restack_lifted`/`restack_aligned`, `nut_grasped`/`nut_aligned`) to begin practice from an intermediate scene (e.g. object already grasped) so the agent trains the hard tail; the staged reward then scores only the stages after that sub-goal; fails loudly if the preset has not been built. With hidden tasks (B2): also the name of a preset you built with `preset.py` (`presets/<name>.json`), on the task it was built on; on a hidden task only such a preset |
| `start_mix` | string | none | a mixed start-state pool (core/mix_presets.py, built with `build_mix`): seeds split across presets of one task at a ratio, some from scratch; the staged reward scores the full chain; not with `start_preset`; fails loudly if not built; refused on a hidden task (B2) |
| `reward` | string | `task_completed` | `task_completed` (1.0 if the task's own success check passes, else 0.0); `shaped` (the simulator's staged reward); Python source containing `def reward(r)`; or the path of a `.py` file (relative paths: the workspace) defining `reward(r)`. `r` is the simulator's reply: `task_completed`, `reward`, `sandbox_rc`, `seed`, `log_tail` (keys or attributes); return a float |
| `seed_start` | integer | the lineage's next unused block (`seed_cursor`): the first call of a lineage (no `init`) starts at 810001; a continuation (`init`) starts right after the seeds its lineage has used (`seeds_consumed` in each `adapters/<name>/call.json`); set it to replay seeds | rollout k of the call runs on seed `seed_start + k`; must not reach seeds 1-100 |
| `seeds` | list of integers, or string | none (`seed_start` applies) | the call's rollout seeds, taken in order across prompts and rollouts, e.g. `"810001-810064,820001-820032"` (a range includes both ends); overrides `seed_start`; at least steps x batch x rollouts seeds, none in 1-100; not with `data`, `start_preset` or `start_mix` |
| `note` | string | none | one sentence inserted after the training prompt's Goal line (not a comment: the rollouts see it; evaluation prompts never have it) |
| `goal` | string | none | replaces the training prompt's Goal line (evaluation prompts keep theirs) |
| `time` | string | set by the site: 1 GPU 25 min + 13 min x steps, 2 GPUs 85 min + 17 min x steps, 3 GPUs 30 min + 14 min x steps, at least 2 h (whole minutes, rounded up; the job record's `config` shows the value used) | wall limit of each Slurm job of the call, `HH:MM:SS`; a call whose job reaches it continues from its last saved step (below); once it has continued 3 times it keeps the adapter of its last saved step, as a cancel (result `time_limit`; a preempted or node-failed call likewise, result `preempted` / `node_fail`), or ends `failed` with the fact if none was saved |
| `data` | string | none | a JSONL file of training prompts in your workspace: see Training data below. With `data`, the tasks, seeds, order and steps come from its rows |
| `objective` | string | `grpo` | `grpo` (the practice call above) or `sft` (supervised fine-tuning on your own demonstrations: see SFT below; its spec has `data` and the fields of that section only) |
| `epochs` | integer | 1 | `objective: sft` only: passes over the kept rows |
| `min_reward` | number | 1.0 | `objective: sft` only: rows with `reward` >= this are trained on, the others dropped (a filter, never a weight) |
| `stop_when` | object | none (all `steps` run) | optional early stop: see Early stop below |
A continuation (`init` = an earlier adapter) practises on fresh seeds by default: its lineage's next unused block, recorded in `call.json` as `lineage`, `seed_cursor` (the block allocated) and `seeds_consumed` (the seeds the rollouts actually used). Fresh means the next draw from the same seed space, not a chosen difficulty; set `seed_start` or `seeds` to replay.
Scenes of a call: one train already covers steps×batch×rollouts distinct scenes; set `seeds` to spread scenes or `seed_start` past the parent's range when continuing; sequential continuation remains allowed. `call.json` of a call with `seeds` records them as `seeds` in range form.
## Training data (`data`)
`data` names a JSONL file in your workspace (a path relative to the workspace, or absolute inside it): one line per training
prompt, `{"task": ..., "seed": ..., "variant": ..., "prompt": ...}` (`variant` and `prompt` optional, no other keys):
- `task`: a trainable task. `variant`: another trainable task of the same simulator task (e.g. `stack` with variant `revstack`; revstack runs under a scene shift and practises alone, so a dataset with revstack rows has no rows of any other task); the row then
  trains on `variant`. Any mixture of tasks and variants is allowed.
- `seed`: an integer >= 810001 (seeds 1-100 are the final score's, 800001-809999 are eval.py's dev seeds); all `rollouts`
  rollouts of the row run on that seed.
- `prompt`: replaces the task's user message for that row only (the system message stays). A row without `prompt` trains on
  the task's eval prompt, checked byte for byte before training; a row with `prompt` is not checked and counts as a prompt
  override, a method choice recorded with the adapter (`data.prompt_overrides` and `data.label` in training.json).
- Rows train in file order, `batch` rows per step: the row count must be a multiple of `batch`, and the call runs
  rows / batch steps (omit `steps`, or give that number). The call's tasks come from the rows (omit `task`); `note` and
  `goal` are not accepted with `data`. At most 4096 rows, 16 MB, 65536 characters per `prompt`.
- The file is copied when the call starts; training.json's `resolved_spec.data` and the train's result (`config.data`) record
  its `sha256`, `rows`, rows per task (`tasks`) and `prompt_overrides`.
## SFT (`objective: sft`)
A spec `{"objective": "sft", "data": "<file>.jsonl"}` (optional: `name`, `init`, `epochs` (1), `batch` (16 rows per step), `lr`
(1e-4), `min_reward` (1.0), `time`; no other field) trains the policy's LoRA by supervised fine-tuning (cross-entropy on the program's
tokens only; LoRA rank 32 / alpha 64 on the policy's modules, or `init` continued; without `init` it continues the policy's own init,
as a practice call does). It runs on the small policy profiles (SCOREBOARD.md's `policy:` line names one, e.g. Qwen3-8B).
Availability is per policy profile: the session's turn-0 facts state it (`train objectives for this session's policy (...)`).
- Each line of `data` is `{"task": ..., "seed": ..., "prompt": [{"role": "system" | "user", "content": ...}, ...], "program": ..., "reward": ...}`
  (exactly these keys): `task` a trainable task (a hidden task by the name you see), `prompt` the chat the program answers (the user
  message last; `tasks/<task>/eval_prompt.txt` as messages is the eval prompt of record), `program` the response trained on, `reward`
  a number used only as the `min_reward` filter.
- `seed` is the scene the program ran on: seeds 1-100 (the final score's) and 800001-809999 (eval.py's dev seeds) are refused, so
  no reading you or the final score take is on a scene the policy was fitted on.
- A kept row whose prompt is not the task's eval prompt of record is a prompt override (a method choice): counted in
  `data.prompt_overrides` and labelled, as `note`/`goal` are.
- Steps = ceil(kept rows x epochs / batch); rows train in a fixed shuffled order; a row longer than 4096 tokens is dropped (`call.json`
  `sft_facts.dropped_too_long`). At most 20000 rows, 256 MB, 65536 characters per message or program.
- Building the file: `python3 skills/trainer/sft_rows.py practice adapters/<name> [--min-reward 1] [--steps 3-5] > sft.jsonl` takes a
  finished practice call's rollouts (Output below); `python3 skills/trainer/sft_rows.py rollouts rollouts/<id>.jsonl [--min-reward 1] > sft.jsonl`
  takes rollout.py rows (reward = your self_reward). Both print why each dropped row was dropped.
- Output: `adapters/<name>/` with the adapter, `sft_log.json` (per step: `step`, `loss`, `grad_norm`, `tokens`), `call.json` and
  `training.json` (`resolved_spec.data`: `sha256` of your file, `rows`, `kept`, rows per task, `min_reward`, `prompt_overrides`); the
  train's result shows the same under `config.data`. A cancel or a cluster stop keeps nothing (the adapter is saved at the end).
- Cost: 1 GPU x (0.05 + 0.000695 x steps x batch) canonical GPU-hours (the admission estimate counts every row of the file).
## Early stop (`stop_when`)
Optional. `{"plateau_steps": K, "min_gain": g}` stops the call once K steps in a row pass without the smoothed reward rising more
than g above its best so far; `{"reward_at_least": r}` stops it once the smoothed reward reaches r; with both, the first that
holds stops it. The smoothed reward is the mean `score_mean` of the last 3 steps, so neither can stop a call before step 3
(a call of fewer than 3 steps, or with 3 + K > `steps`, is refused). It is checked after every step. The adapter is the step it
held at (`stop_step`); the call is charged the steps it completed (`steps_run`, which can include a step that finished before the
stop took effect), and `training.json` / `call.json` record `stopped_early: true`, `stop_step`, `stop_reason` (`plateau` or
`target_reward`) and `steps_run`; the call's `state` is `STOPPED` (a finished call, not a failure). Without it, all `steps` run.
## Defaults (identity-v2)
